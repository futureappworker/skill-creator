# Rule 1 - 關係必須具有需求或程式碼依據

- 每條候選關係必須能追溯至使用者需求、已確認的設計約束或既有程式碼。
- 判定關係時必須記錄其依據，以及該依據如何支持關係兩端與關係種類。
- 證據不足時不得建立關係；不得為了讓圖面看似完整而臆造關係。

## Good Example

- `OrderService` 對 `OrderRepository` 的關係有建構子參數作為既有程式碼依據。

```yaml
source: OrderService
target: OrderRepository
relation: dependency
evidence: "既有 OrderService 建構子接收 OrderRepository"
```

## Bad Example

- 相同關係沒有需求或程式碼依據，建立理由僅是補足圖面。

```yaml
source: OrderService
target: OrderRepository
relation: dependency
evidence: "服務通常都需要 Repository，加入後圖面較完整"
```

# Rule 2 - 介面實作與繼承判定

- 類別承諾提供介面定義的操作契約時，必須判定為介面實作，不得判定為類別繼承。
- 類別繼承必須同時符合子類別是父類別的一種（is-a）、子類別可在不破壞既有契約下替換父類別，以及需求確實需要透過父類別型別產生多型行為。
- 任一繼承條件不成立時不得使用繼承，必須優先以組合取得所需行為。

## Good Example

- `CsvExporter` 承諾 `Exporter` 的匯出契約，且不同實作需要透過介面進行多型替換，因此判定為介面實作。

```yaml
source: CsvExporter
target: Exporter
relation: interface-implementation
reason: "CsvExporter 提供 Exporter 契約，呼叫端需替換不同 Exporter 實作"
```

## Bad Example

- 相同情境只因重用匯出行為便判定為類別繼承，沒有證明 is-a、可替換性與父類別多型需求。

```yaml
source: CsvExporter
target: Exporter
relation: inheritance
reason: "CsvExporter 想重用 Exporter 的匯出行為"
```

# Rule 3 - 組合、聚合與一般依賴判定

- 整體擁有部件，且部件生命週期由整體建立、控制並隨整體終止時，必須判定為組合。
- 整體持有可獨立存在、可由外部建立或可被其他物件共享的成員時，必須判定為聚合。
- 一個物件僅透過方法參數、區域變數、回傳值或短暫呼叫使用另一物件，且不持有其所有權時，必須判定為一般依賴。
- 所有權或生命週期證據不足以支持組合或聚合時，不得臆測強所有權，必須判定為一般依賴。

## Good Example

- `Order` 獨占並控制 `OrderLine` 的生命週期，因此判定為組合；`Team` 持有可獨立存在且可共享的 `Member`，因此判定為聚合；`ReportService` 只在方法執行期間使用 `Formatter`，因此判定為一般依賴。

```yaml
- source: Order
  target: OrderLine
  relation: composition
  lifecycle: "Order 建立 OrderLine，Order 刪除時 OrderLine 一併刪除"
  ownership: exclusive
- source: Team
  target: Member
  relation: aggregation
  lifecycle: "Member 由外部建立，離開 Team 後仍可獨立存在"
  ownership: shared
- source: ReportService
  target: Formatter
  relation: dependency
  lifecycle: "Formatter 由呼叫端建立，僅作為 generate 方法參數使用"
  ownership: none
```

## Bad Example

- 相同生命週期與所有權條件被錯誤分類：`OrderLine` 的生命週期受 `Order` 控制卻判定為聚合、可獨立存在的 `Member` 卻判定為組合、暫時使用的 `Formatter` 也被判定為組合。

```yaml
- source: Order
  target: OrderLine
  relation: aggregation
  lifecycle: "Order 建立 OrderLine，Order 刪除時 OrderLine 一併刪除"
  ownership: exclusive
- source: Team
  target: Member
  relation: composition
  lifecycle: "Member 由外部建立，離開 Team 後仍可獨立存在"
  ownership: shared
- source: ReportService
  target: Formatter
  relation: composition
  lifecycle: "Formatter 由呼叫端建立，僅作為 generate 方法參數使用"
  ownership: none
```

# Rule 4 - 依賴方向與耦合限制

- 同一能力存在穩定抽象且依賴端只需要該抽象契約時，依賴方向必須由使用者朝向穩定抽象。
- 不需要具體類別特有能力時，依賴端不得直接耦合具體實作。
- 關係判定不得產生循環依賴；發現候選關係形成循環時，必須移除無依據的關係，或將共同契約置於循環雙方皆可依賴的穩定抽象。

## Good Example

- `CheckoutService` 只需要付款契約，依賴方向朝向穩定的 `PaymentGateway` 抽象，未與特定供應商耦合。

```yaml
source: CheckoutService
target: PaymentGateway
relation: dependency
required-capability: "charge(amount)"
```

## Bad Example

- 相同需求直接依賴具體的 `StripeGateway`，但沒有使用任何具體實作特有能力。

```yaml
source: CheckoutService
target: StripeGateway
relation: dependency
required-capability: "charge(amount)"
```
